## 前言


# Build Tool：构建工具演进史

在日常开发中，我们经常执行 `build`、`test`、`install` 等命令，也会在 CI/CD 平台中看到各种构建任务。构建成功时，万事大吉；构建失败时，却可能需要在 Gradle、npm、数据库、环境变量和依赖仓库之间反复排查。    
有这么多工具这么多任务，再加上**软件工程的复杂程度不断增长，我们单靠手动命令已经难以可靠地管理整个构建过程。**     

于是 **Build Tool（构建工具）** 开始出现，并随之不断发展。  
比较为人熟知的就是 **Java** 从 **Ant** 演进到 **Maven** 和 **Gradle**；前段项目形成 **npm**、**webpack**、**Vite** 等工具组成的生态。

## Build Tool 的产生

在软件开发中，我们编写的代码通常不能直接运行，例如 Java：

```java
public class Main {
    public static void main(String[] args) {
        System.out.println("Hello World");
    }
}
```

需要先经过编译 `javac Main.java`，生成中间文件 `Main.class`，然后才能执行 `java Main` 运行文件。

随着项目规模扩大，除了编译之外，还会涉及：下载第三方依赖、执行单元测试、代码检查、打包等等，这些步骤统称为：**Build（构建）**    
构建的目标是：

> 将源代码转换为可以运行、部署或发布的软件产物。

但如果项目逐渐增加到数百个源文件，并且引入第三方库、自动化测试、资源文件和多个子模块，事情就会变得复杂。  
假设我们有一个包含数百个 Java 文件的大型项目，如果全部手动执行：

```
javac *.java
java ...
jar ...
scp ...
```

会出现很多问题：

1. 操作繁琐：每次发布都需要执行大量命令，容易遗漏步骤。
2. 难以协作：团队成员可能不同的操作流程和顺序会导致不同构建的结果。
3. 依赖管理困难：每个人自己手动下载依赖，版本容易混乱。
4. 构建过程无法复用：相同的命令和操作不断重复，浪费时间且容易出错。

于是构建工具出现了。它们的核心目标非常简单：用配置代替手工操作，让构建过程自动化、标准化和可重复。  
**构建工具**不仅仅是把源代码编译成可执行文件的工具。在现代软件项目中，它还可以负责组织任务、管理依赖、运行测试、生成构建产物，并将这些步骤串联成一条自动化工作流。

## Build Tool 的演进

### Make：构建工具的祖先

**Make** 诞生于 1976 年，主要用于 C/C++ 项目。开发者通过编写：

```makefile
app: main.o utils.o
	gcc main.o utils.o -o app
```

定义：

```text
目标(Target)
依赖(Dependency)
规则(Rule)
```

然后通过执行 `make` 命令，自动完成构建。

**Make** 的一个显著贡献在于其第一次提出了**依赖关系**，即，当 `main.c` 文件被修改了，只重新编译 `main.o`，而不是整个项目重新构建。  
我们现在称之为**增量构建**，只重新构建发生变化的部分，提高编译效率。  
这一思想至今仍然影响着 Gradle、Bazel 等现代构建系统。

不过随着项目增长，配置越来越复杂，**Make** 局限性也随之体现：缺少统一标准、跨平台能力较弱、依赖管理能力不足等。于是开始出现新的构建工具。

### Java 构建工具：从脚本编排到声明式构建

#### Ant 的自动化构建

2000 年左右，Apache 推出了 **Ant**，其目标很明确：

> 为 Java 提供类似 Make 的自动化构建能力。

配置方式采用 **XML**，文件名通常为 `build.xml`：

```xml
<project>
    <target name="compile">
        ...
    </target>
</project>
```

配置完文件后，只需要执行 `ant` 就可以进行自动化构建。由于运行在 JVM 上，Ant 可以在 Windows、Linux、macOS 之间保持一致行为，其跨平台的优势也十分明显。

Ant 灵活，功能强大，且具备可扩展性，但是缺点也比较明显：需要手动在 `xml` 中定义所有步骤、XML 冗长、项目之间结构不统一等。  
由于其可扩展性和灵活性太强，两个团队在没有事先约定的情况下完全可以用不同的命名定义相同的操作：

```text
Team A:
compile → test → package

Team B:
build → verify → deploy
```

久而久之，随着项目变大，维护成本会跟着水涨船高。

#### Maven：约定优于配置

2004 年，**Maven** 出现。它不仅是为了执行构建任务，也与 Java 项目**依赖管理**和标准化的需求密切相关。  
它提出了一个非常重要的思想：

> Convention over Configuration（约定优于配置）

Maven 使用 `pom.xml` 描述项目的元数据、依赖、插件和构建配置。

```xml
<dependency>
    <groupId>junit</groupId>
    <artifactId>junit</artifactId>
    <version>4.13.2</version>
    <scope>test</scope>
</dependency>
```

这段配置声明了项目对 JUnit 的依赖，所谓“约定优于配置”，我们通过 **Maven** 约定了需要什么依赖以及依赖的版本，从而不需要再手动下载 JAR 文件并配置每个文件的路径。

Maven 还提供了约定的项目目录结构和标准化的构建生命周期。比如定义了 `compile`、`test`、`package` 等生命周期阶段，开发者可以通过统一的命令触发相应工作，而不必为每个项目从头编写所有构建步骤。

当然 Maven 也遇到了自己的瓶颈，除了 **XML 过于冗长**之外，其还难以表达动态生成代码、多环境构建、条件判断等复杂的逻辑，因此**配置灵活性有限**。再加上大型项目过多的 `Modules` 会明显延长构建速度，

#### Gradle：Build as Code

**Gradle 诞生于 2007 年**，并于 **2008 年**发布了它的第一个开源版本。它由 Hans Dockter 和 Adam Murdoch 共同设计与开发，旨在结合并超越 Apache Ant 的灵活性以及 Apache Maven 的依赖管理与约定优于配置的特性。它的目标非常明确：

> 保留 Maven 的生态，提供更灵活的构建能力。

因此，Gradle 在 Maven 等工具已有的基础上，进一步提供了灵活的任务模型、插件机制和可编程的构建配置。

**Gradle** 支持 Groovy DSL 和 Kotlin DSL  
我定义一个名为 `hello` 的 Task，并在任务执行时输出一条信息：

```kotlin
tasks.register("hello") {
    doLast {
        println("Hello Build")
    }
}
```

**Task 任务**是 Gradle 的核心概念，如 `compileJava`，`test`，`jar` 等。Gradle 的构建过程可以根据任务依赖关系形成任务图，即 **Dependency Graph**，再按相应规则执行任务。  
与 Maven 相比，Gradle 在任务编排和构建逻辑定制方面更加灵活，同时也提供**增量构建**和**构建缓存**等能力。对于没有变化的任务会直接复用历史结果。

相比 XML，**Gradle** 脚本本身就是代码，因此可以处理条件判断，循环，封装函数等复杂逻辑。  
不过，复杂的业务逻辑可能会带来更高的维护难度（比如有很多的 `if` 或者 `for` 语句）。也因此，Gradle 的出现并不意味着对 Maven 的取代。Maven 的标准化和约定仍然具有很大价值，Gradle 则适合需要更灵活构建模型的项目。

**Java 构建工具的演进并不是简单的工具替代，而是构建自动化、依赖管理和项目标准化能力不断发展的过程。**

### JavaScript 构建工具：从脚本引用到模块化工程

早期，页面没那么复杂，不需要那么多效果，我们通常直接把 **JavaScript** 写在 **HTML** 中，或者通过多个 `<script>` 标签引入：

```html
<script src="utils.js"></script>
<script src="app.js"></script>
```

这种方式简单直接。但随着应用规模增长，开发者逐渐需要解决模块组织、第三方依赖、代码转换和资源优化等问题。  
需要注意的是，JavaScript 的**包管理**、**模块打包**和**构建自动化**并不是同一条工具演进路线。它们逐渐结合，形成了今天的前端工程化体系。

在缺乏成熟工程工具的情况下，开发者可能需要手动下载第三方 JavaScript 文件，将它们放进项目目录，再通过 HTML 引入。这种方法不仅需要自行管理库文件及其版本，还要在更新时手动处理文件。  
当 `<script>` 标签数量变得庞大，其维护变得愈发困难，而且加载顺序也不能出错。再加上当时 JavaScript 没有模块系统，所有变量都挂到全局，带来了著名的 **Global Namespace Pollution（全局命名空间污染）**

#### npm：包管理工具

**npm （Node Package Manager）** 是 JavaScript 生态中重要的 **包管理工具（Package Management Tool）**，其由多个部分组成，包括**命令行工具（CLI）**、**Registry** 和用于发现软件包的网站。

开发者可以将依赖声明在 `package.json` 中：

```json
{
  "name": "demo",
  "version": "1.0.0",
  "scripts": {
    "build": "webpack"
  },
  "devDependencies": {
    "webpack": "^5.0.0"
  }
}
```


其中：

- `scripts` 定义项目可以执行的命令。
    
- `devDependencies` 声明开发和构建阶段需要的软件包。
    
- npm 根据项目配置解析并安装依赖。
    

执行：

```bash
npm install
npm run build
```

这两条命令承担着不同的工作：第一条主要负责安装依赖，第二条则执行项目定义的构建脚本。

npm 并不会因为拥有 `run build` 命令，就自动成为所有前端构建工作的执行引擎。真正完成构建的工具取决于项目脚本的定义。

### 3.3 第三阶段：模块化与打包工具

随着 JavaScript 模块化能力的发展，项目不再只是少量独立脚本，而是由大量相互依赖的模块组成。

模块打包工具可以分析这些模块之间的依赖关系，并将它们组织为适合浏览器加载的产物。

以 webpack 为例，它能够从入口模块出发，分析依赖关系，并根据配置生成构建产物。

这类工具还可以配合插件和 Loader，处理 CSS、图片、代码转换及其他资源。

此时，npm 和 webpack 的职责已经很清晰：

- npm 负责软件包的安装与管理，并提供脚本执行入口。
    
- webpack 负责模块分析、资源处理与打包。
    
- JavaScript 编译或转换工具可以负责将某些语言特性转换为目标环境支持的代码。
    

它们协同工作，但不是同一个工具。

### 3.4 第四阶段：现代前端构建工具

随着前端应用越来越复杂，开发者对开发服务器启动速度、热更新、生产构建和配置体验提出了更高要求。

Vite 是现代前端构建工具的代表之一。

在开发模式下，Vite 利用浏览器原生 ES Modules 等机制，减少开发服务器启动时必须完成的工作，并提供快速的开发反馈。

在生产构建方面，Vite 则通过构建工具链处理应用资源，生成适合部署的产物。

现代前端工程化不只是打包代码，还涉及开发服务器、代码转换、资源处理、构建优化和开发体验。

不过，npm、webpack 和 Vite 仍然不能简单地视为同一类别：它们在工具链中承担的职责不同。
